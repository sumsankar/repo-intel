3. Security Findings

🔴 CRITICAL  [auth] JWT tokens delivered via URL query parameters
File: src/app/modules/call-back/call-back.component.ts · Lines 26–29

The SSO callback URL delivers AccessToken, RefreshToken, and IdToken as plain URL query parameters (/callback?AccessToken=eyJ...&RefreshToken=...). These tokens are permanently logged in:

  • Browser history (visible to anyone with device access)
  • Web server / proxy / CDN access logs
  • The Referer header of any subsequent navigation to a third-party resource
  • GitLab CI runner logs if callback is triggered during automation

This violates OAuth 2.0 best practices (RFC 9700 / OAuth 2.1) which mandate tokens be delivered via fragment identifiers (#) or POST bodies, never query strings.

Use the Authorization Code flow with PKCE. Receive the authorization code (not tokens) in the callback URL, then exchange it for tokens via a backend POST to the token endpoint. Tokens never appear in the URL. If that is not possible, use the hash fragment (#access_token=...) which is not sent to servers or logged.
🔴 CRITICAL  [auth] JWT tokens stored in localStorage — accessible to any JavaScript
File: src/app/services/data-store.service.ts · Lines 33–39 · Also: interceptor.service.ts, auth.guard.ts

AccessToken, RefreshToken, and IdToken are stored in localStorage via the DataStoreService.setItem() wrapper. localStorage is accessible to any JavaScript running on the page, including injected scripts from third-party libraries, browser extensions, or XSS payloads. A single XSS vulnerability in any of the 30+ third-party dependencies can result in full session takeover.

Store tokens in httpOnly cookies (set by the server, not readable by JavaScript). The backend API should set Set-Cookie: AccessToken=...; HttpOnly; Secure; SameSite=Strict on login. The Angular interceptor then automatically sends cookies with each request via withCredentials: true (already partially wired in auth.service.ts). This eliminates the entire localStorage token attack surface.
🟠 HIGH  [config] production: false committed in app-config.json
File: src/assets/config/app-config.json · Line 2

The committed app-config.json file has "production": false. This is the default config that ships in the built image and is overridden at deploy time via docker cp. However, if the CI inject step fails silently, the container runs in non-production mode against whatever backend URL is in the file — currently a localhost backend that would fail all API calls, or a dev environment. The risk is that the failure mode is invisible to users (white-screen rather than a meaningful error).

Set "production": true as the default in the committed template. The inject step should be treated as critical — add a health check after the config inject that verifies the container returns HTTP 200 before the deploy stage marks success.
🟠 HIGH  [headers] All HTTP security headers missing from nginx.conf
File: nginx.conf

The nginx server block contains zero security headers. Five critical headers are absent:

  • X-Content-Type-Options: nosniff — MIME-type sniffing attacks
  • X-Frame-Options: DENY — clickjacking (embed in iframe)
  • Content-Security-Policy — XSS, data injection, mixed content
  • Strict-Transport-Security — HTTPS downgrade attacks
  • Referrer-Policy: no-referrer-when-downgrade — token leakage via Referer header
Add to the server {} block:
add_header X-Content-Type-Options "nosniff" always;
add_header X-Frame-Options "DENY" always;
add_header Content-Security-Policy "default-src 'self'; script-src 'self' https://cdn.jsdelivr.net; style-src 'self' 'unsafe-inline';" always;
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
add_header Referrer-Policy "no-referrer-when-downgrade" always;
🟠 HIGH  [cors] Wildcard CORS on /assets exposes app-config.json to any origin
File: nginx.conf · Lines 18–20

The /assets location sets add_header Access-Control-Allow-Origin *;. This makes all assets — including app-config.json which contains the Unleash client key, internal API base URLs, and SSO URL — accessible to arbitrary cross-origin requests from any website.

Replace the wildcard with the application's own origin: add_header Access-Control-Allow-Origin "https://hrms.pal.tech" always; or remove the header entirely if cross-origin asset loading is not intentionally required.
🟠 HIGH  [build] Source maps enabled and optimization disabled in production Angular build
File: angular.json · Lines 128–131 (production configuration)

"optimization": false and "sourceMap": true are set in the production build configuration. This means:

  • Full TypeScript source code is served to every end-user browser via .map files
  • No tree-shaking, no minification — bundle size is 3–10× larger than necessary
  • Internal service names, API endpoint paths, business logic, and model structures are exposed
Set "optimization": true and "sourceMap": false in the production configuration. If error tracking (Sentry, etc.) needs source maps, use "sourceMap": {"scripts": false, "styles": false, "hidden": true} to generate server-side-only source maps that are never served publicly.
🟠 HIGH  [xss] bypassSecurityTrustResourceUrl used without URL validation
Files: consent-documents.component.ts:250, 326 · document-status.component.ts:574

Three calls to DomSanitizer.bypassSecurityTrustResourceUrl() bypass Angular's built-in sanitization for resource URLs. If this.fileUrl or fileUrl is derived from user input, an API response, or a URL parameter without strict validation, an attacker could inject a javascript: or data: URI to execute arbitrary code in the iframe context.

Before calling bypassSecurityTrustResourceUrl(), validate that the URL matches a strict allowlist pattern (e.g., must start with https://storage.pal.tech/). Reject any URL not matching the pattern. Add a unit test that asserts rejection of javascript: and data: schemes.
🟡 MEDIUM  [secrets] Unleash client key committed to app-config.json
File: src/assets/config/app-config.json

The Unleash frontend client key (hrms:development.87ac9fdac02ec9a3469ee508c76513d43a1fddd15048a354eb397424) is committed to the repository. While frontend Unleash keys are considered lower-risk (read-only, public-facing), they should not be tracked in source control because: (1) the committed value is the dev key, which may differ from prod; (2) rotation requires a code change and redeploy rather than a config change.

Move the Unleash key to the runtime app-config.json injected at deploy time. The committed file should contain a placeholder: "clientKey": "REPLACE_AT_DEPLOY".
🟡 MEDIUM  [secrets] Hardcoded Microsoft Teams webhook URLs in Jenkinsfile
File: Jenkinsfile · post { always { ... } } block

Two live Teams incoming webhook URLs are hardcoded in the Jenkinsfile committed to source control. Anyone with read access to the repository can post arbitrary messages to internal Teams channels used for deployment notifications.

Move both webhook URLs to the Jenkins credentials store as Secret text credentials. Reference via withCredentials([string(credentialsId: 'teams-webhook-dev', variable: 'TEAMS_HOOK')]). Rotate the existing webhook endpoints.
🔵 LOW  [auth] HTTP status 0 treated identically to 401 in interceptor
File: src/app/services/interceptor.service.ts · Line 54 · Comment: "Don't change to 401"

The interceptor triggers the token refresh flow on both status === 0 (network error / CORS failure) and status === 401 (unauthorized). A network failure will attempt to refresh the token and potentially expose the refresh token over a broken connection. The comment in the code actively discourages fixing this.

Handle status === 0 separately — surface a network error to the user rather than attempting a token refresh. Fix the underlying issue that originally required treating 0 as 401.

🟠 HIGH  [ci] No test stage in either pipeline — tests never run automatically
Files: .gitlab-ci.yml, Jenkinsfile · Policy: GOV-DEV-002

Both CI pipelines build and deploy without running ng test. The 107 spec files are never executed in CI. Additionally, karma.conf.js has singleRun: false — if ng test were added to CI without this change, the test runner would hang indefinitely because it waits for interactive input.

Add a test stage before build in .gitlab-ci.yml. First update karma.conf.js: set singleRun: true, browsers: ['ChromeHeadless'], and add coverage thresholds. Then add: script: npm run test -- --watch=false --browsers=ChromeHeadless. Install Chrome on the CI runner.
🟠 HIGH  [ci] No lint stage — ESLint runs only via bypassable pre-commit hook
Files: .gitlab-ci.yml, .lintstagedrc.json

Lint enforcement relies on Husky pre-commit hooks, which can be bypassed with git commit --no-verify. There is no npm run lint step in either CI pipeline. Unlinted code ships to UAT with no automated gate.

Add a lint job to .gitlab-ci.yml: script: npm run lint. This runs the existing .eslintrc.json configuration and fails the pipeline on any ESLint error.
🟠 HIGH  [ci] No security scanning in pipeline
File: .gitlab-ci.yml

No SAST, dependency vulnerability scanning (npm audit), or container image scanning runs at any pipeline stage. Vulnerabilities in npm packages and the nginx base image go undetected until they appear in a security report.

Add three security gates to .gitlab-ci.yml: (1) npm audit --audit-level=high in the build stage; (2) GitLab SAST template (include: template: Security/SAST.gitlab-ci.yml); (3) Trivy container scan post-push (trivy image $IMAGE_NAME --exit-code 1 --severity HIGH,CRITICAL).
🟡 MEDIUM  [ci] No node_modules caching in GitLab CI
File: .gitlab-ci.yml · build stage

Every pipeline run executes a full npm install (downloading all packages from scratch). For an Angular 17 project with 35+ direct dependencies this adds 2–3 minutes to every build.

Add a cache: block to the build job: key: ${CI_COMMIT_REF_SLUG}-npm, paths: [node_modules/, .npm/], policy: pull-push.
🟡 MEDIUM  [ci] No manual approval gate before UAT; no production pipeline

deploy_uat triggers automatically on any release/* branch push. There is no production deployment stage anywhere. Production deployments appear to be entirely manual (outside the documented pipeline).

Add when: manual to deploy_uat. Add a deploy_prod stage with when: manual, environment: production, and a protected environment requiring approval from a senior engineer.
