Executive Summary
The HRMS API is a mature, feature-rich ASP.NET Core (.NET 10) Human Resource Management System built on a well-structured 4-tier architecture with 10 projects, 1,041 files, and comprehensive HR domain coverage spanning attendance, timesheets, leave, payroll, penalties, and reporting. However, the repository is in a critically unsafe state: production credentials (database password, JWT signing keys, SMTP passwords, OAuth secrets) are hard-coded in a committed appsettings.local.json; the Login() method bypasses all authentication by hard-coding admin@shepherd.com for every request; and DES encryption -- broken since the 1990s -- protects integration secrets. The single most important thing to fix immediately is to rotate every credential in appsettings.local.json, remove that file from git history, and implement a proper secrets manager before this system handles any real employee data.

🚨 Critical & High Priority Findings
  • Critical SECURITY [secrets] -- Production credentials committed to git -- database password (Hrms$321), JWT signing keys, SMTP passwords, OAuth client secrets, and DES encryption keys all hard-coded in appsettings.local.json which is tracked in version control.
    HRMS.API/appsettings.local.json:9,14,26,40-41,56-60,67,75
    Fix: Rotate every credential immediately. Remove file from git history with git filter-branch or BFG. Move all secrets to Azure Key Vault or environment variables. Add appsettings.local.json to .gitignore.
  • Critical SECURITY [auth] -- Authentication bypass -- Login() always authenticates as admin -- the endpoint sets valid = true unconditionally and issues a JWT for the hard-coded user admin@shepherd.com (AccountID: 2) regardless of submitted credentials. Any username/password combination grants admin access.
    HRMS.API/Controllers/AccountController.cs:41,51-54
    Fix: Implement real credential validation against the database. Return 401 Unauthorized on failure. Issue tokens for the actual authenticated user, not a hardcoded admin.
  • Critical SECURITY [crypto] -- DES encryption (56-bit -- cryptographically broken) -- Integration secrets encrypted/decrypted using DES with an 8-character hard-coded key. DES can be brute-forced in hours on commodity hardware.
    JWTAuth/Helpers/ServiceIntegrationAuthHelper.cs:17-41
    Fix: Replace with AES-256-GCM. Generate a 32-byte random key stored in Key Vault. Use a random 16-byte IV per encryption operation.
  • Critical SECURITY [config] -- CORS allows any origin with credentials -- SetIsOriginAllowed(origin => true) combined with AllowCredentials() enables any website to make authenticated requests to this API, enabling CSRF and credential theft.
    HRMS.API/Program.cs:226-230
    Fix: Replace with .WithOrigins("https://your-frontend.pal.tech"). Never combine AllowAnyOrigin with AllowCredentials.
  • Critical DEPENDENCY [cve] -- ASP.NET Core 2.3.0 packages with known CVEs referenced in net10.0 projects -- Microsoft.AspNetCore.Mvc.Abstractions, Mvc.Core, Mvc.Formatters.Json, and Antiforgery are all version 2.3.0 from 2020, 7+ major versions behind 10.0.1, carrying multiple known CVEs including deserialization vulnerabilities.

  • Critical SECURITY [config] -- SQL Server connection transmitted in plaintext (Encrypt=False) -- database traffic including queries and employee PII travels unencrypted over the network.
    HRMS.API/appsettings.local.json:9 -- DefaultConnection
    Fix: Set Encrypt=strict;TrustServerCertificate=false in connection string. Use Active Directory authentication to eliminate stored SQL credentials.
  • Critical DEVOPS [ci] -- No tests executed in CI/CD pipeline -- neither the GitLab CI nor Jenkinsfile includes a dotnet test step despite three test projects existing. Untested code ships to every environment.
    .gitlab-ci.yml (entire file) · Jenkinsfile (entire file)

🔒 Security

Risk Level: 🔴 CRITICAL

Summary: Multiple critical vulnerabilities coexist: production credentials committed to git, a login endpoint granting admin access to anyone, DES encryption protecting integration secrets, CORS open to all origins with credentials, and SQL connections transmitted in plaintext -- any one alone would block production; together they represent an existential security risk for an HR system handling employee PII.

  • Medium [config] -- Missing security response headers -- no Content-Security-Policy, Strict-Transport-Security, X-Frame-Options, X-Content-Type-Options, or Referrer-Policy, leaving the API exposed to clickjacking and content injection.
    HRMS.API/Program.cs (no header middleware configured)
    Fix: Add a middleware pipeline step or use NetEscapades.AspNetCore.SecurityHeaders to set all recommended headers.
  • Medium [crypto] -- 8-byte DES encryption key/IV stored as plain strings in appsettings -- "PALTECHH"/"TECHPALL" are trivially guessable, compounding the DES weakness.
    HRMS.API/appsettings.local.json:40-41 (EncryptionSettings.Key / .IV)
    Fix: After migrating to AES-256-GCM, generate a 256-bit random key from Key Vault. Use a random 16-byte IV per encryption operation.
  • Medium [access-control] -- JWT access token lifetime 24 hours, refresh token 30 days -- excessive for an HR system handling sensitive payroll and PII. A stolen token remains valid for a full working day.
    HRMS.API/appsettings.local.json -- JWTSettings AccessTokenExpiryMinutes:1440 / RefreshTokenExpiryMinutes:43200
    Fix: Reduce access token to 15-30 minutes and refresh token to 7 days. Implement token revocation on logout.
  • Medium [injection] -- String array joining without type validation in EmployeeRepository -- employeeIds, departmentIds, gradeIds joined with string.Join without verifying values are numeric before passing to stored procedure.
    HRMS.API.Repository/EmployeeRepository.cs:88-94
    Fix: Validate all ID values are numeric (long.TryParse) before inclusion. Use table-valued parameters instead of comma-separated strings.
  • Medium [hygiene] -- No SECURITY.md -- no vulnerability disclosure policy, security contact, or supported versions matrix.
    / (root -- file absent)
    Fix: Create SECURITY.md with a security contact email, disclosure policy, and list of supported versions receiving security patches.
  • Medium [hygiene] -- No Dependabot configuration -- vulnerable NuGet packages are not automatically flagged. Given the 7+ major version gaps already found, automated scanning is essential.
    / (no .github/dependabot.yml)
    Fix: Add .github/dependabot.yml for NuGet ecosystem with weekly schedule. Or enable GitLab built-in dependency scanning.
  • Medium [logging] -- Authentication and authorization events not logged -- failed logins, permission denials, and sensitive operations (data exports, employee exits) produce no audit trail.
    HRMS.API/Program.cs:193-213 (Serilog configuration)
    Fix: Add structured log entries for auth success/failure, authorization failure, and sensitive data access with user ID and IP address.
  • Low [hygiene] -- .gitignore does not explicitly exclude appsettings.*.json variants -- appsettings.Development.json or appsettings.Production.json with secrets could be committed in future.
    .gitignore
    Fix: Add appsettings.*.json, appsettings.local.json, *.env to .gitignore. Use dotnet user-secrets for local development.
